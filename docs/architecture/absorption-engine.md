# Absorption Engine

## Purpose
Discover useful software capabilities and make them part of Senorita's coherent architecture where legally and technically appropriate.

## Absorption modes
### Source absorption
Selectively reuse and adapt actual source code. Preserve notices, satisfy licence obligations, refactor into Senorita module boundaries, add tests and record provenance.

### Component absorption
Adopt a package or library as a dependency. Pin versions, review transitive dependencies, scan vulnerabilities and track upstream maintenance.

### Knowledge absorption
Study algorithms, architectures, protocols and engineering practices, then independently implement an approach when direct copying is unsuitable or prohibited.

## Evaluation pipeline
Discover → inspect maintenance/releases → inspect code/dependencies → determine licence → sandbox analysis → static/security checks → compare alternatives → adoption proposal → policy decision → isolated integration → verification → provenance record.

## Evaluation criteria
Licence obligations, security posture, maintenance, code quality, tests, documentation, dependency risk, architectural fit, performance, platform compatibility and long-term maintenance cost.

Stars and popularity are discovery signals, not quality guarantees.

## Mandatory legal rules
A public GitHub repository is not automatically permission to copy or redistribute. If no explicit licence exists, source absorption is not approved until rights are clarified. Preserve copyright/licence notices and assess copyleft obligations before adoption.

Every absorption record captures source URL, exact commit/version, retrieval date, files/modules, licence, notices, modifications, dependencies, scan results, destination module, tests and approval decision.
